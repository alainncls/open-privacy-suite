# Privacy Requirements & Guarantees

This page describes what the Privacy Proxy system guarantees about data visibility, what its current limitations are, and what operators must configure to achieve full protection.

---

## What Is Protected

Private addresses and their transaction activity are hidden from unauthorized viewers. The system enforces this at two layers:

1. **JSON-RPC proxy layer** — when a client queries the Ethereum node directly through the proxy (e.g. `eth_getTransactionByHash`), responses are filtered based on whether the caller is a participant in the transaction. Non-participants receive `null` or have individual entries removed from arrays.

2. **Explorer API layer** — when the block explorer fetches structured data through the Privacy Proxy's Explorer API, each entity (transaction, log, token transfer, etc.) is individually processed through the redaction engine. Addresses are replaced with `[PRIVATE]`, values zeroed, and entries dropped according to the viewer's permission level and the [disclosure level](/docs/disclosure) assigned to each address.

Both layers work in concert. A viewer who bypasses the block explorer and queries the JSON-RPC endpoint directly will receive the same privacy enforcement — the proxy is the sole gateway.

## Protection by Data Type

### Transactions

| Field | What an unauthorized viewer sees |
|-------|----------------------------------|
| `from` | `[PRIVATE]` |
| `to` | `[PRIVATE]` |
| `value` (ETH amount) | Hidden (zero / omitted) |
| `inputData` (calldata) | Hidden (omitted) |
| `nonce` | Hidden (omitted) — prevents transaction-count fingerprinting of the sender |
| `error` / `revertReason` | Hidden (omitted) |
| `contractAddress` (deploy txs) | See known limitations below |
| Gas parameters (`gasUsed`, `gasPrice`, etc.) | Visible — see known limitations below |

When both the sender and receiver of a transaction are private, the transaction is dropped from the response entirely. A viewer cannot determine that the transaction exists.

When one side is private and the other is public, the transaction remains visible but the private party is shown as `[PRIVATE]` and all sensitive financial fields are hidden.

### Token Transfers

| Field | What an unauthorized viewer sees |
|-------|----------------------------------|
| `from` | `[PRIVATE]` |
| `to` | `[PRIVATE]` |
| `value` (token amount) | Hidden (zero / omitted) |
| `tokenAddress` | Visible — the token contract itself is public infrastructure |

The same drop rule applies: if both sides are private, the transfer record is removed entirely.

### Event Logs

Event log visibility depends on the privacy level of the **emitting contract**, not the transaction parties.

| Scenario | What an unauthorized viewer sees |
|----------|----------------------------------|
| Emitting contract is private (Hidden) | Entire log entry removed — viewer cannot see that the log exists |
| Emitting contract is private (Redacted) | Log kept; emitter address shown as `[PRIVATE]`; all topic slots and `data` field zeroed |
| Emitting contract is public | Log kept; indexed address parameters (topics[1]–topics[3]) scanned: private addresses zeroed |
| Emitting contract is public + ABI registered | Non-indexed address parameters in the `data` field also scanned; private addresses zeroed |

For anonymous Solidity events (declared with the `anonymous` keyword), `topics[0]` may contain an indexed address and is scanned as well.

<Callout type="note">
  Indexed address parameters in event topics are always scanned when the emitting
  contract is visible, regardless of whether an ABI is registered. ABI registration
  only affects scanning of the non-indexed `data` field.
</Callout>

### Token Holders

| Scenario | What an unauthorized viewer sees |
|----------|----------------------------------|
| Address is Hidden | Holder entry removed from the list entirely |
| Address is Redacted | Entry shown as `[PRIVATE]`; balance and percentage hidden |
| Address is visible | Full holder entry shown |

### Blocks

Block-level data is always public. Blocks are consensus-layer infrastructure, not user activity, and there is no grant or visibility mechanism for block producers.

| Field | Visibility |
|-------|-----------|
| `number`, `hash`, `timestamp` | Always public |
| `gasUsed`, `gasLimit`, `baseFeePerGas` | Always public |
| `miner` | Always public |
| `transactions` (hashes only) | Always public |
| `transactions` (full objects) | Per-transaction participant check applied; non-participant transactions removed |
| `logsBloom` | Always public — see known limitations below |

## Disclosure Levels

Each address in the system is assigned a disclosure level that controls how much information about it is shared with different classes of viewers. See [Selective Disclosure](/docs/disclosure) for the full reference.

---

## Known Limitations

The following limitations are known and accepted in the current release. They are documented here so operators can make informed decisions about their deployment.

### 1. Event log `data` fields without a registered ABI

When an event log's emitting contract does not have a registered and verified ABI, the non-indexed `data` field is returned without scanning. If a private address appears as a non-indexed parameter in an event emitted by an unverified contract, that address will not be redacted from the `data` field.

**What to do:** Register ABIs for all contracts whose events include address parameters. See [What Operators Must Do](#what-operators-must-do) below.

### 2. Block `logsBloom` is not zeroed

The `logsBloom` field in block headers is a Bloom filter over the addresses and topics of all logs in the block. It contains hashed representations of addresses, not raw addresses. A viewer who already knows a specific target address can probe whether that address has any log activity in a given block in O(1) time.

This is a probabilistic, one-bit query: it can confirm activity but not reveal the address to a viewer who does not already know it. The risk is low in practice — an attacker must already possess the address they are testing, and the filter produces false positives. Zeroing the bloom for every block would require scanning all block logs against the private address registry on every block request, which is prohibitively expensive at scale.

### 3. Contract deployment: deployed address visible when deployer is private

When a private address deploys a contract, the transaction's `contractAddress` field (the address of the newly deployed contract) is currently not stripped. An unauthorized viewer can see the address of the contract that was deployed, even though the deployer's identity is shown as `[PRIVATE]`. The deployed contract may be discoverable in the block explorer and could be correlated with subsequent activity.

**Mitigation:** Ensure deployed contracts are registered to the same organization as the deployer, so their activity is also subject to access control.

### 4. Gas parameters are not hidden

Gas fields (`gasUsed`, `gasPrice`, `maxFeePerGas`, `maxPriorityFeePerGas`, `gasLimit`) are visible to all viewers, including those who cannot see the transaction parties. Gas parameters do not directly identify an address and are available to all participants in the network via the RPC layer regardless of this proxy.

### 5. Value inference from public address balance history

When a transaction involves one private address and one public address, the `value` field is hidden. However, the transferred amount can still be inferred by comparing the public address's balance at adjacent blocks:

```
transferred ≈ balance(block N−1) − balance(block N) − (gas_used × gas_price)
```

All inputs to this calculation are accessible through the block explorer for public addresses. This requires deliberate cross-block correlation rather than direct reading, but it is feasible. Stripping the `value` field removes the direct leakage path; it is not a complete financial privacy guarantee for mixed-party transactions.

## What Operators Must Do

To achieve the maximum redaction coverage described in this document:

1. **Register ABIs for all privacy-sensitive contracts.** Event log `data` field scanning (for non-indexed address parameters) only activates when the emitting contract has a registered and verified ABI. Without an ABI, addresses embedded in non-indexed log parameters are not redacted.

   To register an ABI, use the admin API:
   ```
   POST /admin/contracts/{address}/abi
   Content-Type: application/json
   {"abi": [...]}
   ```

2. **Assign all deployed contracts to the correct organization.** The redaction engine determines visibility by checking whether a contract address is registered to an organization. Contracts that are not registered to any organization are treated as public. Register contracts with the same organization as their deployer.

3. **Assign disclosure levels to sensitive addresses.** Addresses that are not explicitly registered receive default public visibility. Ensure that all addresses that should be private are registered to an organization and assigned the appropriate disclosure level. See [Selective Disclosure](/docs/disclosure).

<Callout type="warning">
  Addresses that are not registered to any organization are treated as public and
  will not be redacted, even if they appear as counterparties in transactions
  involving private addresses.
</Callout>
