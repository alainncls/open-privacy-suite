# Configuration Reference

All Open Privacy Suite configuration is driven by environment variables. This page documents every variable, their defaults, and how they interact across development and production modes.

---

## Required in Production

These variables **must** be set when `ENVIRONMENT=production`. The server will refuse to start without them.

| Variable | Description |
|----------|-------------|
| `JWT_SECRET` | Secret for signing access tokens |
| `JWT_REFRESH_SECRET` | Secret for signing refresh tokens |
| `VERIFIER_ID` | Your Privado verifier DID |
| `ADMIN_API_TOKEN` | Shared token for admin API authentication (M2M / bootstrap) |
| `DATABASE_URL` | PostgreSQL connection string |

## Runtime Tracing

The proxy uses `debug_traceCall` to validate all addresses touched by transactions before forwarding them to the node. This provides comprehensive cross-organization isolation:

- **All internal CALL/DELEGATECALL/STATICCALL targets are validated** against RBAC permissions
- **Custom Multicall contracts are detected** -- any contract batching calls will have all targets validated
- **CREATE/CREATE2 in runtime is blocked** -- prevents unauthorized contract deployment
- **Precompiles (0x01--0x09) are always allowed**

**Node requirements:**

- Upstream node must support `debug_traceCall` (Geth, Anvil, Erigon, Nethermind)
- For Geth: the `--http.api debug` flag is required

**Performance impact:**

- Adds approximately 50--200 ms latency per transaction
- Tiered validation skips tracing for calls to known org-owned addresses
- Caching reduces overhead for repeated patterns

## Extra RPC Namespaces

To support chain-specific JSON-RPC methods (e.g. Linea, zkSync, Optimism), create a JSON config file and point to it with `EXTRA_RPC_NAMESPACES_FILE`:

```bash
EXTRA_RPC_NAMESPACES_FILE=./rpc-namespaces.json
```

The file format is a versioned JSON object. Each method entry can be a plain string (passthrough) or an object with an `alias` field to inherit access control from a standard method:

```json
{
  "version": 1,
  "namespaces": {
    "Linea": [
      {"method": "linea_estimateGas", "alias": "eth_estimateGas"},
      {"method": "linea_getProof", "alias": "eth_getProof"},
      "linea_getTransactionExclusionStatusV1"
    ]
  }
}
```

| Field | Description |
|-------|-------------|
| `version` | Schema version (currently `1`). Required for forward compatibility. |
| `namespaces` | Map of display label to method list. The key appears as the section heading in the admin UI. |

### Method entries

Every method must specify an `alias` — a standard Ethereum method it inherits access control and response filtering from. This ensures contract-level checks, storage slot tiering, deployment detection, and participant-based response filtering apply consistently.

```json
{"method": "linea_estimateGas", "alias": "eth_estimateGas"}
```

The proxy will reject the config at startup if any method is missing an alias.

Extra methods appear as toggleable methods in the admin dashboard group access form, under their namespace heading. They do not require claims and are not included in the standard role presets.

When `*` (wildcard) is used in a group's allowed methods, extra methods are included in the expansion.

A ready-to-use example is provided in `rpc-namespaces.example.json` — copy and customize it:

```bash
cp rpc-namespaces.example.json rpc-namespaces.json
```

| Auth Session | 10 minutes | Time to complete the auth flow |

## RPC API Keys

Each RBAC group can have an API key for the upstream RPC node. This enables per-group rate limiting and usage tracking on the upstream side.

<EnvTable vars={[
  { name: "RPC_API_KEY", default: "(none)", description: "Global fallback API key for the upstream RPC node. Used when no group-specific key is configured." },
  { name: "RPC_API_KEY_ENCRYPTION_KEY", default: "(none)", description: "Hex-encoded 32-byte key for encrypting API keys at rest. Required in production. Generate with: openssl rand -hex 32" },
  { name: "MAX_CONCURRENT_REQUESTS", default: "50", description: "Maximum concurrent in-flight requests per authenticated user." },
]} />

Per-group keys are configured in the admin dashboard under group access settings. Keys are encrypted at rest in production and masked in API responses (only last 4 characters visible).

The client's IP is forwarded to the upstream node via `X-Forwarded-For` for upstream rate limiting.

## Environment Modes

### Development (`ENVIRONMENT=development`)

- `/auth/verify` endpoint enabled for manual testing
- JWT secrets auto-generated if not set
- `REQUIRE_PROOF_OF_HUMANITY` defaults to `false`
- Mock tokens accepted: `mock.{did}` or `mock.jwz.token.{did}`
- Mock-login users are auto-granted the `admin` claim (instant admin dashboard access)

### Production (`ENVIRONMENT=production`)

- `/auth/verify` endpoint disabled
- JWT secrets required (server will not start without them)
- `REQUIRE_PROOF_OF_HUMANITY` defaults to `true`
- `VERIFIER_ID` required
- `ADMIN_API_TOKEN` required (server will not start without it)

<Callout variant="warning" title="Development-only features">
  Mock tokens and the `/auth/verify` endpoint are disabled in production mode. Do not rely on them for integration testing against a production deployment.
</Callout>


## Database

### Connection

Uses pgx v5 with the standard `database/sql` interface.

```bash
# Local development
DATABASE_URL=postgres://postgres:postgres@localhost:5432/privacy_proxy?sslmode=disable

# Docker
DATABASE_URL=postgres://postgres:postgres@postgres:5432/privacy_proxy?sslmode=disable
```

### Migrations

Uses Tern v2 with embedded migrations in `internal/db/migrations/`.

```bash
# Run migrations
make db-migrate

# Create new migration
make db-new-migration name=add_feature
```

<Callout variant="info" title="Migration policy">
  Migrations are expand-only in production. Never use DROP in UP migrations. If a migration needs undoing, create a new forward migration.
</Callout>

## Trusted Proxies

For Docker environments, the server trusts `X-Forwarded-For` from:

- `172.16.0.0/12` (Docker networks)
- `127.0.0.1` (localhost)

Adjust in `internal/server/server.go` if your deployment requires additional trusted ranges.

## Example .env

```bash
# Required for production
ENVIRONMENT=production
JWT_SECRET=your-secure-secret-here
JWT_REFRESH_SECRET=your-refresh-secret-here
VERIFIER_ID=did:polygonid:polygon:main:your-verifier-did

# Database
DATABASE_URL=postgres://user:pass@host:5432/dbname?sslmode=require

# Ethereum node
NODE_URL=https://eth-mainnet.alchemyapi.io/v2/your-key

# Privado
PRIVADO_RPC_URL=https://rpc-mainnet.privado.id

# ProofOfHumanity (optional)
BILLIONS_ISSUER_DID=did:polygonid:polygon:main:billions-issuer-did
REQUIRE_PROOF_OF_HUMANITY=true

# Admin API
ADMIN_API_TOKEN=your-admin-token-here

# RPC API key encryption (generate with: openssl rand -hex 32)
RPC_API_KEY_ENCRYPTION_KEY=your-64-char-hex-string-here

# Public URL
BASE_URL=https://your-domain.com
```
